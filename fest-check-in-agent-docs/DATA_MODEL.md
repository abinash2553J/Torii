# Data Model, Constraints and RLS Plan

## 1. Core entities

-   `profiles`: application profile linked to `auth.users`.
-   `events`: initial single event.
-   `gates`: event entry points.
-   `event_volunteers`: volunteer-to-event/gate assignments.
-   `tickets`: one ticket per attendee per event.
-   `check_ins`: successful admissions only.
-   `scan_attempts`: accepted, rejected and conflict audit outcomes.

## 2. Required constraints

### Tickets

-   Primary key on `id`.
-   Foreign key to event and attendee profile.
-   Unique `(event_id, attendee_id)` for one ticket per attendee per
    event.
-   `token_version` is positive.
-   Revocation is represented explicitly.

### Check-ins

-   Unique `ticket_id`: at most one successful admission per ticket.
-   Unique `scan_id`: idempotent scan submission.
-   Composite foreign key `(ticket_id, event_id)` to ensure event
    consistency.
-   Composite foreign key `(gate_id, event_id)` to ensure gate belongs
    to event.

### Scan attempts

-   Unique `scan_id`.
-   Outcome constrained to known values.
-   Source constrained to `online` or `offline_sync`.
-   Keep attempts separate from successful check-ins.

## 3. Additional recommended fields

Depending on implementation, add: - `events.registration_opens_at`,
`registration_closes_at`. - `events.registration_enabled`. -
`tickets.token_version`. `tickets.revoked_at` is required for MVP ticket
revocation. - `check_ins.scanned_at` generated by server. -
`check_ins.scanner_id` as an installation identifier, not an
authorization credential. - `scan_attempts.details` with a strict
allowlist of safe diagnostic metadata. - `sync_batches` only if
batch-level tracking is needed.

Do not store signed QR tokens in database tables. The offline client
must keep a token in IndexedDB only while its scan is pending; clear it
when the final server outcome is stored.

## 4. Transaction requirements

The service-role-only online database function must: 1. Accept the
volunteer ID only from the trusted Edge Function. 2. Verify volunteer
assignment for event and gate. 3. Validate event status and ticket
association. 4. Validate ticket not revoked. 5. Handle repeated
`scan_id` idempotently. 6. Attempt unique check-in insert. 7. Determine
whether conflict is same ticket or same scan ID. 8. Write one audit
outcome. 9. Return a typed result.

The successful check-in and accepted audit row should commit together.
If audit insertion fails, the transaction should fail rather than leave
an untraceable admission.

Use RPCs for privileged writes. Do not grant direct client
insert/update/delete on `check_ins`, `scan_attempts`, ticket signing
fields or volunteer assignments.

## 6. RLS implementation notes

-   Enable RLS on every exposed table.
-   Use `auth.uid()` and ownership/assignment checks.
-   Avoid recursive policy dependencies.
-   Keep policy helper functions minimal and secure.
-   For `SECURITY DEFINER` functions, set a fixed `search_path`, qualify
    object names and restrict `EXECUTE` grants.
-   Test policies using separate attendee, volunteer, organizer and
    anonymous sessions.
-   Never rely only on frontend route guards.

## 7. CSV export

Export successful check-ins, not registrations. Suggested columns: -
attendee name - attendee email, only if operationally required - ticket
reference - event - gate - check-in time - source / reconciliation
status where useful

Restrict export to organizers. Escape CSV cells to prevent spreadsheet
formula injection. Avoid including sensitive internal IDs unless needed.
